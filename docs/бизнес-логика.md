# Бизнес-логика Shopee

Документ описывает, как заказ проходит через код этого репозитория: сервис заказов `shopee-project` и сервис склада `warehouse-service`. Это поведение текущей реализации. В конце отдельно собрано, где выполнение расходится с файлом «Постановка задачи.pdf».

Система оформляет заказ интернет-магазина. Она принимает состав корзины, проверяет и резервирует товар на складе, сохраняет заказ в PostgreSQL и публикует событие в Kafka. Оплаты, каталога цен, доставки как отдельного процесса и личного кабинета покупателя в системе нет. Цена приходит в запросе клиента.

## Участники

| Участник | Где живёт | Что делает |
|---|---|---|
| Клиент API | снаружи | создаёт, читает и отменяет заказ |
| Сервис заказов | порт 8080, БД `localhost:5432/shopee-project` | считает сумму, выбирает статус, пишет заказ, зовёт склад, шлёт события |
| Сервис склада | порт 8081, БД `localhost:5433/warehouse_service_db` | хранит остаток, резервирует и возвращает штуки |
| Kafka | `localhost:9092` | принимает четыре топика событий заказа |
| Складской слушатель | внутри warehouse-service | читает те же топики и пишет их в лог |

Склад для сервиса заказов — внешний HTTP по адресу `WAREHOUSE_URL` (по умолчанию `http://localhost:8081`).

## Данные заказа

Входящий контракт `POST /api/orders`:

```json
{
  "customerId": "UUID",
  "items": [
    { "productId": "UUID", "quantity": 5, "price": 199.99 }
  ],
  "deliveryAddress": {
    "city": "Москва",
    "street": "Ленина",
    "house": "10",
    "apartment": "25"
  }
}
```

Ответ, который сервис собирает после обработки:

```json
{
  "orderId": "UUID",
  "status": "CONFIRMED | WAITING_STOCK | CREATED | CANCELLED",
  "totalAmount": 999.95,
  "createdAt": "2024-01-15T10:30:00",
  "estimatedDelivery": "2024-01-18"
}
```

В ответе нет позиций, адреса и покупателя. Их можно восстановить только из базы.

Таблица `orders`: id, customer_id, order_status, total_amount, created_at, estimated_delivery, cancelled_at, city, street, house, apartment.

Таблица `order_items`: id, order_id, product_id, quantity (> 0), price. Удаление заказа каскадом удаляет позиции. В работающем API физического удаления нет.

Таблица `product_stock` на складе: одна строка на товар. Поля `available_quantity` (можно продать), `reserved_quantity` (уже обещано заказам), `version`. Оба количества не могут быть отрицательными. `product_id` уникален.

Резерв не хранит номер заказа. Склад знает только «по этому товару зарезервировано N штук», без разбивки по заказам.

## Статусы

| Статус | Кто его ставит | Смысл в этой реализации |
|---|---|---|
| `CREATED` | маппер при сборке заказа; повторно — ветка сбоя склада | заказ записан, склад на проверке не ответил, ждёт повторной обработки |
| `CONFIRMED` | `createOrder`, когда все позиции зарезервированы | товар обещан покупателю, штуки лежат в `reserved` |
| `WAITING_STOCK` | метод `handleOutOfStock` | склад ответил, что штук не хватает |
| `DELIVERED` | никем через API | статус объявлен, перевод в него отсутствует |
| `CANCELLED` | `PATCH .../status` или `DELETE` | мягкое удаление: строка остаётся |

Переходы, которые код реально выполняет:

```text
                 проверка склада недоступна
               +------------------------------+
               |                              |
               v                              |
запрос ----> CREATED ------------------> CONFIRMED ----> CANCELLED
               |                              ^
               |  available = false           |
               +-----------> WAITING_STOCK    |
                                              |
DELIVERED объявлен в enum и никуда не ведёт --+
```

`WAITING_STOCK` в текущем `createOrder` не достигается: до вызова `handleOutOfStock` срабатывает исключение. Это разобрано в сценарии 2.

Список `GET /api/orders` скрывает `CANCELLED`. `GET /api/orders/{id}` такой заказ возвращает.

## Создание заказа

`POST /api/orders`.

### 1. Проверка входа

Сначала срабатывает `@Valid` на контроллере:

- `customerId` обязателен;
- список позиций не пустой;
- у позиции есть `productId`, `quantity` не меньше 1, `price` строго больше нуля;
- адрес обязателен, город, улица и дом не пустые, квартира может отсутствовать.

Ошибка этой проверки — HTTP 400, код `INVALID_ORDER`, текст по полям.

Затем `OrderValidator` не участвует. Сервис вызывает `CheckResponseUtil.validateCreateOrder` и повторяет ту же проверку покупателя, непустого списка, количества, цены и наличия адреса. Для обычного HTTP-запроса до этой проверки доходит уже проверенное тело.

### 2. Сборка заказа в памяти

Маппер создаёт `Order` со статусом `CREATED` и `createdAt = сейчас`. Идентификатор ещё пустой, его выдаст база при сохранении.

`assembleOrder` для каждой позиции:

- привязывает позицию к заказу;
- прибавляет к сумме `price × quantity`.

Потом ставит `totalAmount` и `estimatedDelivery = сегодня + 3 дня`. Дата считается в момент сборки, до ответа склада. Если заказ сохранится как `CREATED` или `WAITING_STOCK`, у него будет та же дата «через 3 дня».

До этого момента в базе ничего нет, склад не вызывался.

### 3. Цикл по позициям

Позиции обрабатываются по очереди, сверху вниз. Общей транзакции на весь заказ нет: HTTP-вызовы склада идут вне транзакции базы заказов.

Для каждой позиции:

1. `GET /api/warehouse/check?productId={id}&qty={qty}`.
2. Разбор ответа.
3. Если разбор пропустил позицию дальше — `POST /api/warehouse/reserve` с телом `{ productId, quantity }`.
4. Проверка, что резерв вернул `available: true`.

Вызов проверки обёрнут в retry и circuit breaker `warehouse`. Повторяются таймаут, обрыв сети, HTTP 5xx и ошибки ввода-вывода: до 3 попыток, пауза 2 секунды, множитель 2, потолок 10 секунд. Ответы 4xx повторно не шлются и circuit breaker их не считает поломкой склада. После исчерпания попыток fallback бросает `WarehouseUnavailableException`.

Дальше развилка зависит от того, какое исключение вылетело и в каком месте цикла.

### Сценарий 1. Все позиции есть

Склад на проверку вернул `available: true`. Резерв прошёл и тоже вернул `available: true` (склад после успешного резерва всегда ставит `available = true` и `status = RESERVED`).

Так для каждой позиции. Когда цикл закончился:

1. Статус в памяти меняется на `CONFIRMED`.
2. `orderRepository.save` пишет заказ и позиции. С этого момента заказ есть в базе.
3. На каждую позицию уходит своё сообщение в топик `order.confirmed`. Ключ — `orderId`. Тело: `orderId`, `productId`, `quantity`, `occurredAt`. Отправка синхронная, ожидание ответа брокера до 5 секунд. Ошибка сериализации или отправки бросает `IllegalStateException` уже после сохранения заказа.
4. Сущность мапится в ответ со статусом `CONFIRMED`.

Контроллер пропускает этот ответ через переключатель статусов. Переключатель знает строки `CREATED` и `ACCEPTED`. Статуса `ACCEPTED` в домене нет. `CONFIRMED` попадает в ветку по умолчанию и превращается в `NoSuchStatusException`.

Клиент получает HTTP 400, код `NO_SUCH_STATUS`, текст «Нет подходящего статуса: CONFIRMED». Заказ при этом уже `CONFIRMED`, резерв уже списан, событие уже ушло в Kafka. Повтор того же запроса создаёт второй заказ и второй резерв.

### Сценарий 2. Товара не хватает

Склад на проверку жив и вернул `available: false`, статус ответа склада `INSUFFICIENT`.

`processStockResponse` на `available: false` бросает `StockResponseException`. Вызов `handleOutOfStock` стоит следом и не выполняется.

Исключение никем отдельно не обработано. Общий обработчик отвечает HTTP 500, код `INTERNAL_ERROR`. Заказ в базу не пишется. Событие `order.waiting-stock` не отправляется.

Если к этому моменту предыдущие позиции цикла уже прошли `reserve`, их штуки остаются в `reserved_quantity`. Заказа, к которому они относятся, в базе заказов нет.

Метод `handleOutOfStock`, который постановка описывает для этого случая, делает другое, но из `createOrder` до него ход не доходит:

- статус `WAITING_STOCK`;
- сохранение заказа;
- по каждой позиции событие `order.waiting-stock` с `orderId`, `productId`, `occurredAt`. Поля `requestedQuantity` и `availableQuantity` в событии есть, сервис их не заполняет;
- ответ со статусом `WAITING_STOCK`.

Если бы ответ дошёл до контроллера, `WAITING_STOCK` тоже попал бы в ветку по умолчанию и стал бы HTTP 400.

Отдельный путь к нехватке — гонка уже после успешной проверки. Проверка сказала «есть», параллельный заказ забрал остаток, `reserve` получил конфликт. Склад отвечает HTTP 409 `INSUFFICIENT_STOCK`. Сервис заказов это 4xx не переводит в `WAITING_STOCK`: клиент RestTemplate получает ошибку клиента, fallback пробрасывает её как есть, общий обработчик отвечает 500. Уже взятые резервы предыдущих позиций остаются.

Товар, которого нет в `product_stock`, склад отвечает HTTP 404 `NOT_FOUND`. Для сервиса заказов это тоже необработанное 4xx и ответ 500. Заказ не создаётся.

### Сценарий 3. Склад недоступен на проверке

Таймаут, сеть или HTTP 5xx на `checkStock` исчерпали retry. Клиент бросает `WarehouseUnavailableException`. Цикл ловит именно это исключение и вызывает `handleWarehouseError`:

- статус явно ставится `CREATED`;
- заказ сохраняется вместе со всеми позициями и уже посчитанной суммой;
- на каждую позицию уходит `order.pending-review`: `orderId`, `productId`, `quantity`, `occurredAt`;
- в лог пишется фраза «Товара нет на складе» — это текст про другой сценарий, в топик при этом уходит `order.pending-review`.

Ответ имеет статус `CREATED`. Контроллер на эту строку отвечает HTTP 201.

Ветка срабатывает на первой упавшей проверке и прекращает цикл. Позиции, которые выше по списку уже зарезервированы, не освобождаются. Заказ при этом записан как `CREATED`, то есть по правилам отмены резерва у него ещё нет: `hasReservedStock` смотрит только на `CONFIRMED`.

Пустое тело успешной проверки обрабатывается иначе. `processStockResponse` бросает `WarehouseUnavailableException` уже снаружи `try/catch`. Заказ не сохраняется, клиент получает HTTP 503 `WAREHOUSE_UNAVAILABLE`.

Сбой на `reserve` (таймаут или 5xx) тоже снаружи этого `try/catch`. Заказ не сохраняется, клиент получает 503, ранее взятый резерв остаётся на складе.

### Сценарий 4. Отмена через PATCH

`PATCH /api/orders/{id}/status`

```json
{ "status": "CANCELLED", "reason": "покупатель передумал" }
```

Оба поля обязательны. Любой статус кроме `CANCELLED` — HTTP 400 `NO_SUCH_STATUS`. Других переходов этот метод не делает, в том числе в `DELIVERED`.

Дальше:

1. Заказ ищется по id. Нет строки — HTTP 404 `ORDER_NOT_FOUND`.
2. `OrderValidator.canCancel`. `DELIVERED` и повторный `CANCELLED` — HTTP 409 `CANNOT_CANCEL`. В теле ответа текущий статус вклеен в `message`. Отдельного поля `currentStatus` нет. `CREATED`, `CONFIRMED` и `WAITING_STOCK` отменять можно.
3. Пока статус ещё старый, сервис запоминает, был ли резерв. Резерв считается взятым только у `CONFIRMED`.
4. Маппер ставит статус из запроса и `cancelledAt = сейчас`. Причина в таблицу заказов не пишется.
5. Если резерв был, по каждой позиции `POST /api/warehouse/release` с `{ productId, quantity }`. Ответ с `available: false` или пустое тело прерывают отмену исключением. Часть позиций могла уже вернуться на склад, заказ ещё не сохранён как отменённый.
6. Заказ сохраняется.
7. В `order.cancelled` уходит одно сообщение на заказ: `orderId`, `reason`, `occurredAt`.
8. Клиент получает HTTP 200 и тело заказа. Статус в теле берётся из того объекта, который вернул мок или маппер после сохранения. В рабочем пути это уже `CANCELLED`.

`reason` живёт только в событии Kafka.

### Удаление

`DELETE /api/orders/{id}` помечен как мягкое удаление.

Метод находит заказ, запрещает повторную отмену уже отменённого (HTTP 409 `INVALID_ORDER_STATUS`) и записывает статус `CANCELLED`.

Этот путь не проверяет `DELIVERED`, не пишет `cancelledAt`, не вызывает склад и не публикует `order.cancelled`.

Если так удалить `CONFIRMED`, штуки остаются в `reserved_quantity`. Следующий PATCH видит `CANCELLED` и отвечает 409, поэтому до возврата резерва ход уже не доходит.

Ответ успешного DELETE — HTTP 204 без тела.

## Чтение

`GET /api/orders/{id}` — заказ по id вместе со статусом, суммой, датой создания и датой доставки. Отменённый тоже возвращается. Нет id — 404.

`GET /api/orders` — страница заказов со статусом, отличным от `CANCELLED`. По умолчанию 20 записей, сортировка `createdAt` по убыванию. Ответ: `content`, `page`, `size`, `totalElements`, `totalPages`, `last`. Фильтра по покупателю в API нет, хотя индекс `(customer_id, order_status)` в базе есть.

## Как склад меняет остаток

### Проверка

`GET /api/warehouse/check?productId=&qty=`

Склад ищет строку товара. Нет строки — 404. Есть строка — ответ:

- `available` = доступного количества хватает на `qty`;
- `availableQuantity` — текущий доступный остаток, без вычитания запроса;
- `status` = `OK` или `INSUFFICIENT`.

Метод помечен `@Cacheable` с ключом «товар + количество». Рабочий `CacheManager` с временем жизни в основном коде склада не объявлен (класс с TTL 5 секунд лежит в тестовых исходниках). При включённом `@EnableCaching` проверка кэшируется в памяти процесса. Повтор того же запроса может получить прежний `available: true` после того, как резерв уже уменьшил остаток. Источник истины при записи — сам резерв: он ещё раз сравнивает количество под блокировкой версии.

### Резерв

`POST /api/warehouse/reserve`

Под оптимистической блокировкой по `version`:

```text
если available < quantity → 409, остаток не меняется
иначе available = available - quantity
      reserved  = reserved  + quantity
```

Успех: `available: true`, `status: RESERVED`, в `availableQuantity` уже новый остаток. Конфликт версии повторяется до 3 раз с паузой 100 мс.

Два заказа на один товар увеличивают общий `reserved`. Склад не помнит, какая часть принадлежит какому заказу.

### Возврат

`POST /api/warehouse/release`

```text
если reserved < quantity → 409
иначе reserved  = reserved  - quantity
      available = available + quantity
```

Успех: `available: true`, `status: RELEASED`.

Возврат тоже идёт по товару и количеству. Он уменьшает общий котёл `reserved`, а не резерв конкретного заказа.

## Kafka

Продюсер сериализует событие в JSON строкой и кладёт `ProducerRecord(topic, orderId, json)`. Вызов ждёт подтверждения брокера до 5 секунд.

| Топик | Когда код его шлёт | Сколько сообщений |
|---|---|---|
| `order.confirmed` | все позиции зарезервированы и заказ сохранён | по одному на позицию |
| `order.waiting-stock` | из `handleOutOfStock`, до которого создание сейчас не доходит | по одному на позицию |
| `order.pending-review` | проверка склада упала и заказ сохранён как `CREATED` | по одному на позицию |
| `order.cancelled` | успешный PATCH-отмены | одно на заказ |

Слушатель склада подписан на все четыре топика, группа `warehouse-service`. Он разбирает JSON, пишет лог и выходит из метода. Остаток он не меняет. Ошибочный JSON ловится внутри слушателя, метод завершается штатно, смещение коммитится, сообщение повторно не читается.

В `docker-compose` у брокера выключено автосоздание топиков. Бины топиков объявлены в интеграционном тесте сервиса заказов. В обычном запуске продюсер пишет в топики, которые compose сам не заводит.

Комментарии в слушателе говорят про резерв, проверку остатка и возврат товара. Если эти методы начать менять остаток, получится второе списание и второй возврат поверх уже выполненных REST-вызовов.

## Ошибки, которые видит клиент сервиса заказов

| Ситуация | HTTP | Код |
|---|---|---|
| Заказ не найден | 404 | `ORDER_NOT_FOUND` |
| Тело запроса не прошло `@Valid` или ручную проверку | 400 | `INVALID_ORDER` |
| PATCH со статусом кроме `CANCELLED`; ответ создания со статусом кроме `CREATED` | 400 | `NO_SUCH_STATUS` |
| PATCH доставленного или уже отменённого | 409 | `CANNOT_CANCEL` |
| DELETE уже отменённого | 409 | `INVALID_ORDER_STATUS` |
| Проверка или резерв склада недоступны и исключение вышло из сервиса | 503 | `WAREHOUSE_UNAVAILABLE` |
| Нехватка товара, 404/409 склада, сбой Kafka после сохранения, прочие исключения | 500 | `INTERNAL_ERROR` |

Форма тела: `code`, `header`, `message`.

Успешные коды, которые контроллер умеет отдать на создание: HTTP 201 только для статуса-строки `CREATED`. HTTP 202 завязан на строку `ACCEPTED`, которую сервис не возвращает.

## Сквозной пример

Две позиции, на складе обеих хватает.

1. Клиент шлёт POST с двумя items.
2. Сумма считается в памяти, статус в памяти `CREATED`, доставка через 3 дня.
3. Первая позиция: check → reserve. `available` уменьшился, `reserved` вырос.
4. Вторая позиция: то же самое.
5. Статус становится `CONFIRMED`, строка появляется в `orders`, две строки в `order_items`.
6. В `order.confirmed` уходят два JSON с одним `orderId` и разными `productId`.
7. Складский слушатель оба сообщения логирует и остаток не трогает.
8. Контроллер видит статус `CONFIRMED` и отвечает клиенту 400.
9. Для покупателя оформление выглядит неуспешным. Для склада и базы заказ уже подтверждён.

Одна позиция есть, вторая отсутствует, первая уже зарезервирована.

1. Первая позиция резервируется.
2. Вторая проверка возвращает `available: false`.
3. `StockResponseException`, заказ не сохраняется.
4. Клиент получает 500.
5. Штуки первой позиции остаются в `reserved` без заказа.

Проверка первой позиции падает по таймауту три раза.

1. Резерва ещё нет.
2. Заказ сохраняется как `CREATED`.
3. В `order.pending-review` уходит событие на каждую позицию.
4. Клиент получает 201 и статус `CREATED`.

## Где выполнение расходится с постановкой

Постановка задаёт такие ответы создания:

- товар есть → статус `CONFIRMED`, HTTP 201, топик `order.confirmed`;
- товара нет → статус `WAITING_STOCK`, HTTP 202, топик `order.waiting-stock`;
- склад недоступен после retry → статус `CREATED`, HTTP 202, топик `order.pending-review`;
- отмена → `CANCELLED`, `cancelledAt`, возврат резерва, топик `order.cancelled`, HTTP 200;
- ошибка публикации в Kafka откатывает запись в базе (`@Transactional` на методах сервиса);
- в базе есть таблица истории `order_status_history`;
- в логах есть `correlationId`.

В этом репозитории создание с товаром в наличии сохраняет `CONFIRMED` и шлёт событие, а клиенту отдаёт 400. Ветка `WAITING_STOCK` написана и не вызывается: нехватка товара становится 500. Недоступность склада на проверке сохраняет `CREATED` и шлёт `order.pending-review`, клиенту при этом отдаётся 201. `DELETE` отменяет заказ без возврата резерва и без события. Методы сервиса заказов без `@Transactional`: сохранение и отправка в Kafka — две отдельные операции, падение брокера запись не откатывает. Таблицы истории статусов нет. В шаблоне лога место под `correlationId` есть, фильтр, который кладёт туда значение запроса, не написан.
